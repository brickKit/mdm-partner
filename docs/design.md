# mdm/partner 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态与规则、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`；跨组件的规则在装配项目的协议 02（投影的来源）、协议 07（引用的生命周期、资格与解析）与决定 D20–D22。

## 边界

拥有业务伙伴（企业或自然人）的共同身份、名称、税号、正式联系人与地址，以及伙伴在各法人下开通的角色。

| 不在这里 | 归谁 |
| --- | --- |
| 信用额度、信用占用 | `erp/credit` |
| CRM 的私有关系（负责人、公海、共享） | `crm/customer` |
| 法人本身、法人是否可用 | `mdm/org` |
| 伙伴的应收应付、付款 | `erp/finance`、`erp/payment` |
| 客户特有的字段（行业、来源渠道） | 扩展字段（协议 08），标准逻辑不读 |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 伙伴种类 | 企业或自然人 | `kind`：`organization`、`person` |
| 名称与译名 | 一个主名称，加按语言标签的译名 | `name`、`names` |
| 税号 | 国家内的纳税识别号，可以没有；写入时统一转大写、去掉空格，存的就是规范化后的值 | `tax_id` |
| 重复候选 | 同一国家、同一税号的其他伙伴（含已暂停与已退役的）；新建与修改提交之后另读一次返回，由人决定是否合并（D22）。并发新建的两个重复伙伴可能互相看不到对方，人工合并兜底 | `duplicate_candidates` |
| 正式联系人、地址 | 伙伴自己的联系人与地址（开票、收货、注册）；随伙伴一起版本化 | `contacts`、`addresses` |
| 角色 | 伙伴在一个法人下的一种身份：客户、供应商、员工往来（员工作为收款对象）、关联方（对应集团内的一个法人）；每个伙伴、每种角色、每个法人至多一个。本版只有客户角色 | `partner_role` |
| 伙伴银行账户 | 对方的收款账户；自然人的是受限字段（以后） | — |
| 合并与别名 | 重复的伙伴经人确认合并成一个存续伙伴，原身份成为别名，解析时返回存续伙伴（以后，D22） | — |
| 资格 | 新单据能否在某法人以某用途引用某伙伴的证据；用途 `sell` 需要客户角色 | `Eligibility`、`eligibility` |
| 批量解析 | 按身份回答当前数据、已并入、墓碑或不存在 | `Resolve` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `partner` | 伙伴：种类、名称与译名、国家、税号、状态、联系人与地址（JSON）、搜索列、版本 | `retired` 不再变；身份永不复用，本版不删除 |
| `partner_role` | 角色：伙伴、角色种类、法人（`mdm/org` 的身份，不透明引用）、状态、缺省币种、付款条件、版本 | 同上；唯一键（伙伴、角色、法人） |

以后还有：伙伴银行账户、合并记录与别名、销毁后的墓碑。

每条记录带版本，每次变化在同一个事务里以完整状态事件发布（协议 02 的来源义务）。不分区，也不转层（协议 11：在线可变的主数据）；列表按名称的索引分页，税号查重用（国家，税号）的索引。税号查重只有普通索引，没有唯一约束：重复是提示，不是错误。

## 状态与规则

伙伴与角色各有一套状态，互不牵连（伙伴暂停不改变角色的状态，资格查询两者都看）：

| 当前状态 | 命令 | 结果 |
| --- | --- | --- |
| `active` | 暂停 | `suspended` |
| `suspended` | 恢复 | `active` |
| `active`、`suspended` | 退役 | `retired` |
| `retired` | 任何修改 | 拒绝：`STATE_CONFLICT`（409） |

不变量：

- 身份永不复用；已合并或已销毁的伙伴不接受新的资格引用（合并与销毁本版不做）。
- 角色只能在**存在且启用**的法人下开通：开通与修改角色之前，在事务之外同步问 `mdm/org`；`mdm/org` 答不上时不开通，答“依赖不可用”，不当作“法人不存在”（协议 07）。
- 同一国家的税号重复时提示，由人决定是否合并（D22），不拒绝；合并不成环。
- 员工往来角色只由员工组件经业务确认开通，不开放客户或供应商业务（D69）；每个法人至多对应一个关联方伙伴（D72）。（这两种角色本版不做）
- 资格：伙伴 `active`，并且该法人下该用途的角色 `active`，才 `eligible`；否则回答缺的是哪一部分（`not_found`、`partner_<状态>`、`role_not_opened`、`role_<状态>`），并带取证时刻。**资格查询不看法人的状态**：新单据还要向 `mdm/org` 取法人的证据，由引用方负责（协议 07 的资格引用的提交检查）。
- 资格的有效期 W 是 30 秒（协议 07 的起始值），从引用方发出查询时算起；引用方在 W 之内提交，过期重新取证，不缓存回答。

## 命令与查询

| 命令或查询 | 用户面或系统面 | 权限键 |
| --- | --- | --- |
| 新建伙伴（带 `Idempotency-Key`，返回重复候选） | 用户面 | `mdm.partner.create` |
| 修改伙伴；伙伴的状态 | 用户面 | `mdm.partner.edit` |
| 伙伴列表（按名称排序；按状态、种类筛选；`q` 搜名称、译名与税号）与单条读取 | 用户面 | `mdm.partner.read` |
| 开通或修改客户角色；角色的状态 | 用户面 | `mdm.partner_role.manage` |
| 列出伙伴的角色；资格（用户面的查询） | 用户面 | `mdm.partner.read`（角色资源的读取操作是 `mdm.partner_role.read`，用于授权视图） |
| 合并与拆回 | 用户面 | `mdm.partner.merge`（本版答“能力不支持”） |
| 来源方法 `Snapshot`、`Read`；资格查询；批量解析（一次最多 500 个） | 系统面 | `mdm.partner.system.read` |

确切的路径、字段与错误在 `contract/openapi.yaml` 与 `contract/proto/`。

## 事件

流 `mdm.partner`（4 个分区），两种完整状态事件：`mdm.partner.changed.v1`、`mdm.partner_role.changed.v1`。以后加“已合并”与“已销毁”（附要擦除的字段类别）。事件的 schema 同时是来源方法里 `data` 的格式与 OpenAPI 里伙伴、角色的形状，改一处就是改三处（`contract/README.md`）。订阅方投影角色就够做显示与报表；资格判断不用投影，走资格查询（伙伴不是水位来源，协议 07）。

## 依赖

- `mdm/org`（必需）：开通角色时确认法人存在且启用。用同步查询而不是投影：开通角色是低频的写，同步查询最简单，而且总是最新。
- 身份、授权（必需）；`infra/audit`（可选，兼任证据存储）：缺时审计记录留在本地（协议 03）；销毁与擦除的意图写入证据，缺时走外部告警渠道（协议 15）。附件（可选）：证照，缺时不能上传资料文件。

## 数据范围

本版没有维度：能读伙伴的用户看到全部法人的伙伴。按法人限定伙伴的读取要先在资源定义里声明维度（安全 07、09a），列入未决问题。

## 实现状态

实验第 6 步的范围只有客户角色。供应商、员工往来与关联方角色、合并与拆回、伙伴银行账户、销毁与擦除在契约里，调用答“能力不支持”（`CAPABILITY_UNSUPPORTED`，D75）；扩展字段等 SDK 支持后再加。

## 部署与替换

读多写少，适合外壳。同契约的实现可以接替；适用协议 02、07、08、11（在线可变，不转层）、13（数据集）、16（导入模板与期初）、安全 01–09。

## 验证故事

| 故事 | 本版 |
| --- | --- |
| 法人乙未开通客户角色时，下单被拒 | 资格查询答 `role_not_opened`（集成测试）；拒绝由销售做 |
| 同一企业既是客户又是供应商，应收应付各自独立 | 供应商角色本版不做 |
| 重复客户人工合并后，历史订单显示原快照与“已并入”；共享不自动转到存续客户 | 合并本版不做 |
| 报销款付到员工往来角色的银行账户，无权限的人看不到该账户 | 员工往来角色与银行账户本版不做 |

## 未决问题

- **法人暂停时，已开通的客户角色怎样处理**：现在角色不随法人暂停；新单据靠引用方另向 `mdm/org` 取法人证据挡住。是否让资格查询也看法人状态，随第 7 步销售的设计定。
- **按法人的数据范围**：哪些伙伴字段与角色按法人限定读取。
- **合并与拆回**、**伙伴银行账户**（受限字段）、**销毁与擦除**：契约已有位置，实现时补规则与测试。
